# Источники, граф компании и честные ответы

## Подключение модели

| `LLM_PROVIDER` | Что это | Когда |
|---|---|---|
| `gemini` | внешний API, `route: external` | **демо по умолчанию**: умная локальная модель не помещается на ноутбуки команды |
| `openai` | внешний API OpenAI (GPT), `route: external` | ключ `OPENAI_API_KEY`, модель `OPENAI_MODEL` |
| `anthropic` | внешний API Anthropic (Claude), `route: external` | ключ `ANTHROPIC_API_KEY`, модель `ANTHROPIC_MODEL` |
| `local` | любой OpenAI‑совместимый сервер в контуре компании (vLLM, TGI, LM Studio), `route: local` | **пилот**: модель на GPU заказчика; меняются только `LOCAL_BASE_URL` и `LOCAL_MODEL` |
| `ollama` | Ollama, `route: local` | проверка локальной модели на ноутбуке с GPU |
| `fake` | dev‑заглушка без ИИ | только разработка |

Маршрут каждого ответа виден в `route` и `model`; скрытого переключения нет.

## Источники данных

Данные приходят не только из «папки документов», но и из каналов, где на самом деле живёт работа:

| Канал | Коннектор | Формат на хакатоне (синтетика) | В пилоте |
|---|---|---|---|
| Почта | `email_eml` | папка `.eml` (RFC 5322) | IMAP / Exchange / Microsoft Graph |
| Telegram | `telegram_export` | экспорт Telegram Desktop `result.json` | Telegram Bot API (бот в группе) |
| Рабочий чат | `chat_json` | `{"messages": [{id, author, sent_at, text}]}` | Битрикс24 / корпоративный мессенджер |

Описание каналов — `data/sources/channels.json`:

```json
{"id": "tg-production", "kind": "telegram", "name": "Telegram: Производство — оперативный",
 "connector": "telegram_export", "path": "telegram/production/result.json",
 "access_level": "participants", "department_id": "production",
 "member_ids": ["e-morozov", "e-petrova", "e-volkov", "e-kozlova"]}
```

`path` — относительно `data/sources/`. Синхронизация при seed и вручную: `POST /sources/{id}/sync` (директор). Ошибка разбора не роняет стенд: канал получает `status: error` и текст ошибки.

**Права:**
- `participants` — переписку видят **только участники** (для почты: отправитель, получатели и владелец ящика; для чатов — `member_ids`). **Даже директор не читает чужие чаты и письма.**
- `department` — чат подразделения: подразделение и директор.
- `public` — все.
Права применяются в SQL поиска до ранжирования — как для документов.

**Как хранится:** письмо = документ (`kind: email`), чат режется по дням: документ = канал за день, фрагмент = одно сообщение с автором (`author_employee_id`, `author_raw`) и временем (`sent_at`). Цитата в ответе указывает, кто и когда это написал.

| Эндпоинт | Что отдаёт |
|---|---|
| `GET /sources` | видимые пользователю каналы: тип, статус, время синхронизации, число сообщений |
| `POST /sources/{id}/sync` | пересинхронизация (директор), пишется в аудит |

## Граф компании

Узлы: сотрудники, сущности (`data/glossary.json`: поставщики, партии, продукты, оборудование, темы), встречи, пункты протоколов, поручения, документы, письма, сообщения. Рёбра строятся **без LLM**: из связей в БД и словарных упоминаний (основа слова + окончание, «БелЛиста» → «БелЛист»). **У каждого ребра упоминания/авторства есть первоисточник** (`evidence`: цитата, автор, время). Подграф фильтруется правами текущего пользователя — у директора и руководителя он разный.

| Эндпоинт | Что отдаёт |
|---|---|
| `GET /graph?focus=entity:sup-b` | всё про сущность: документы, письма, сообщения, авторы, поручения и решения про неё |
| `GET /graph?focus=employee:e-petrova` | что человек писал, чем владеет, где участвовал |
| `GET /graph?focus=task:t-certificates-1104` | поручение → владелец, встреча, основание в протоколе, сущности и **разговоры о нём вне встреч** |
| `GET /graph?focus=meeting:m-quality-1104` | участники и поручения встречи |
| `GET /graph/focus-options` | список сотрудников и сущностей для выбора центра графа |

Формат: `{focus, nodes: [{id: "type:ref", type, label, ref_id, meta}], edges: [{source, target, type, label, evidence}]}`.

Граф же расширяет поиск: в вопросе «что с БелЛистом?» находятся сообщения и письма, где упомянут «БелЛист», даже без тех же слов.

## Ассистент не выдумывает

`POST /assistant/ask` → `status`:

| status | Что значит | Что показать |
|---|---|---|
| `answered` | каждое утверждение подтверждено цитатой | ответ + сноски (`source_type`, автор, время) |
| `partial` | часть вопроса без основания | ответ + блок «Не подтверждено источниками» (`gaps`) + «Кто может знать» (`experts`) |
| `not_found` | **«Недостаточно данных в доступных вам источниках»**; если источников нет вовсе — модель даже не вызывается | `gaps` + `experts` |
| `refused` | запрещённая категория (оклады, ПДн) | отказ |

Сервер выбрасывает любое утверждение, цитату которого не нашёл в переданном фрагменте, и сообщает об этом в `gaps`. `experts` строится из данных, доступных пользователю: кто писал об этом, кто владеет поручением, чья это зона ответственности.
